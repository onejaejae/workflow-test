# Clarify Skill

모호한 요구사항을 명확한 구현 스펙으로 변환하는 스킬입니다.

## 명확화가 필요한 조건

**중요:** 아래 평가는 **요구사항 텍스트 자체**만 보고 판단합니다. 프로젝트 컨텍스트나 CLAUDE.md 정보는 별개입니다.

다음 중 2개 이상 해당하면 명확화가 필요합니다:

| 평가 항목 | 모호함 판단 기준 | 점수 |
|-----------|------------------|------|
| 기술 스택 | 요구사항에 NestJS, TypeORM, JWT 등 **직접** 명시 없음 | 1 |
| API 경로 | 요구사항에 `/api/v1/...` 형식의 경로 **직접** 포함 없음 | 1 |
| 수용 기준 | 요구사항에 "~하면 성공", "~시 에러" 등 조건 **직접** 명시 없음 | 1 |
| 구체성 | 추상적 표현 사용 (예: "개선", "좋게", "빠르게") | 1 |

**총점 0-1**: 명확함 → 명확화 불필요
**총점 2+**: 모호함 → 명확화 필요

---

## 4단계 명확화 프로세스

### Step 1: 원본 캡처

사용자의 원래 요구사항을 그대로 기록합니다.

```
📝 원본 요구사항: "[사용자 입력 그대로]"
```

### Step 2: 반복 질문

AskUserQuestion 도구를 사용하여 모호한 부분을 명확화합니다.

**질문 우선순위:**
1. **What**: 무엇을 구현해야 하는가? (기능 범위)
2. **Who**: 누가 사용하는가? (사용자/권한)
3. **How**: 어떻게 동작해야 하는가? (기술적 요구사항)
4. **When**: 언제 성공/실패인가? (수용 기준)

**질문 예시:**
- "회원가입에서 어떤 정보를 받아야 하나요? (이메일, 비밀번호, 이름 등)"
- "이메일 중복 시 어떤 에러 코드를 반환해야 하나요?"
- "비밀번호 정책이 있나요? (최소 길이, 특수문자 등)"
- "인증 방식은 JWT를 사용하나요?"

**질문 규칙:**
- 한 번에 최대 3개 질문
- 구체적인 선택지 제공 (가능하면)
- 기본값 제안 (프로젝트 컨벤션 기반)

**금지사항:**
- 질문 후 "가정된 답변"으로 진행 금지
- 사용자 응답을 반드시 기다린 후 다음 단계 진행
- 스스로 합리적이라고 판단한 가정을 세우지 말 것

### Step 3: Before/After 비교

명확화 전후를 비교하여 사용자에게 보여줍니다.

```markdown
## 명확화 결과

### Before (원본)
> [원본 요구사항]

### After (명확화)
> [명확화된 요구사항]

### 추가된 세부사항
- [세부사항 1]
- [세부사항 2]
```

### Step 4: 구조화 출력

다음 형식으로 명확화된 요구사항을 출력합니다.

```markdown
## 명확화된 요구사항

### Goal (목표)
[달성해야 할 결과물]

### Scope (범위)
- 포함: [...]
- 제외: [...]

### Constraints (제약사항)
- [기술적 제약 1]
- [기술적 제약 2]

### Success Criteria (수용 기준)
- [ ] [성공 조건 1]
- [ ] [성공 조건 2]
- [ ] [에러 케이스 1]

### Dependencies (의존성)
- [필요한 기존 모듈/라이브러리]
```

## 출력 → 분석 매핑

Clarify 출력은 Phase 0 분석 항목과 다음과 같이 매핑됩니다:

| Clarify 출력 | Phase 0 분석 항목 |
|--------------|-------------------|
| Goal | 목표 |
| Scope | 범위 |
| Constraints + Dependencies | 기술적 요구사항 |
| Success Criteria | 수용 기준 |

---

## 명확화 스킵 조건 (총점 0-1)

위 평가 기준으로 **총점 0-1점**이면 명확화를 스킵합니다.

**스킵 예시:**
```
POST /api/v1/auth/signup JWT 회원가입 API 구현, 이메일 중복 시 409 Conflict 반환
```

| 평가 항목 | 판단 | 점수 |
|-----------|------|------|
| 기술 스택 | JWT 명시 | 0 |
| API 경로 | `/api/v1/auth/signup` 명시 | 0 |
| 수용 기준 | "이메일 중복 시 409 Conflict" 명시 | 0 |
| 구체성 | "회원가입 API 구현" - 구체적 | 0 |

**총점: 0점** → 명확화 불필요, 바로 진행

## 사용 예시

### 모호한 입력
```
회원가입 API 만들어줘
```

### 명확화 질문
1. "어떤 정보를 받아야 하나요?"
   - 옵션: 이메일+비밀번호 / 이메일+비밀번호+이름 / 기타
2. "인증 방식은 무엇인가요?"
   - 옵션: JWT / Session / OAuth
3. "이메일 중복 시 처리는?"
   - 옵션: 409 Conflict / 400 Bad Request / 기타

### 명확화된 출력
```markdown
### Goal
이메일/비밀번호 기반 회원가입 API 구현

### Scope
- 포함: 이메일 검증, 비밀번호 해싱, 중복 체크
- 제외: 이메일 인증, 소셜 로그인

### Constraints
- NestJS + TypeORM
- bcrypt로 비밀번호 해싱
- JWT 토큰 발급

### Success Criteria
- [ ] POST /api/v1/auth/signup 으로 회원가입 가능
- [ ] 성공 시 201 Created + JWT 토큰 반환
- [ ] 이메일 중복 시 409 Conflict 반환
- [ ] 비밀번호 최소 8자 미만 시 400 Bad Request

### Dependencies
- User 엔티티
- AuthService
- JwtModule
```
